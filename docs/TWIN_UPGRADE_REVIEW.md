# 需求书评审：数字孪生改造 vs 本工程现状

对照对象：外部提供的《数据中心 3D 可视化系统升级改造需求书》。
对照依据：`README.md`、`src/App.jsx`、`src/scene/Infrastructure.jsx`、`src/data/supportSystems.js`、`src/data/roomLayout.js`、`src/data/infraParts.js`、`src/data/roomCameras.js`，以及全 `src/` 的“消防／灭火／门禁／摄像／发电／漏水／接地／防火墙”检索（除 `infraParts.js` 的“柜体接地”外零命中）。

## 一、结论

需求书是一份合格的“机房应该有哪些系统”的清单，但它是一份**只看过截图、没看过代码**的清单。直接用会出现两个问题：

1. **重复建设**：它列为“新增”的 UPS、蓄电池、配电柜、机柜 PDU、母线、环境传感器，本工程已经实现并且带拆解视图，照做等于推翻重做。
2. **漏掉真正的缺口**：消防、门禁与摄像、备用发电机、备份设备、边界路由与防火墙——这五项在 `src/` 里一行都没有，而需求书把它们和已实现项混在一起，没有区分。

另外有 4 处与本项目已确立的设计约束直接冲突（见第四节），其中“模拟故障与告警”和“不提供虚构读数”是产品立场层面的冲突，需要先决策，不是排版问题。

| 蓄电池柜 | 电池模块组已是 UPS 拆解件 01（抽屉式，下半柜） | **已有**（形态不同，可选拆为独立柜） |

| 机柜 PDU | `RackPdu` 组件，C01 已细化到 PDU→PSU 两级 | **已有**（其余 7 柜只画母线分支，README 有明示） |

## 三、事实勘误

1. **N02 不是制冷系统。** `roomLayout.js` 里 N02 是后排网络柜（`x:-3.65, z:-1.15, rotation: π`）。两台 CRAC 在 `[-4.55, 0, -3.65]` 与 `[-3.12, 0, -3.65]`，没有机柜编号。需求书“保留 N02 制冷系统及原有相关管线”如果照做，会改错对象。

2. **供电拓扑顺序写反了。** 需求书写的是“市电 → 配电设备 → UPS → 配电支路 → 机柜 PDU”，而 `supportSystems.js` 的 6 步是“进线 → UPS → 配电柜 → 母线 → 机柜 PDU → 设备 PSU”，这是对的。UPS 必须紧贴负载侧、在配电分路之前；按需求书的顺序，UPS 会去保护整条母线，既不合工程也不合它的容量逻辑。**这一条以现有实现为准，不要改。**

3. **“新增双路供电，避免单点故障”与实际链路矛盾。** 现在 `FEED` 只有一条进线（`[4.62, 1.3, -4.66]`），文案也自认“本示例唯一的上游电源”。要做 A/B 双路，得先加第二条进线几何 + 第二路上游面板 + 重新拉 UPS 输入路径，属于供电章节的结构性改动，不是“补一台设备”。

4. **“顶部桥架 + 消防管路 + 摄像头”在同一高度打架。** 母线在 `y = 2.86`，`floorFade.js` 的墙面淡出 knee 是 2.4、顶部 3.05 归零（见 `HANDOFF.md` S4b）。消防主管与桥架若按需求书“沿顶部桥架规范布置”再往上一档，就会进入淡出带变成半透明残影。新增顶部管线必须落在 2.92 以下，或复用 `floorFade` 的世界坐标采样。

5. **冷通道端门会挡住既有镜头。** `rack-front` 机位在 `[-1.65, 1.3, 2.8]` 正对 C01，`cold-aisle` 在 `[-3.4, 1.55, 1.9]` 沿通道看。加封闭端门等于在这两个机位前面立一块板。若做，端门只能是单侧、且开门状态。

## 四、与本项目已定约束的冲突

| 需求书要求 | 项目既有约束 | 冲突性质 |
| --- | --- | --- |
| 监控总览：设备总数／在线数／告警数／IT 负载／平均温度 | `README` 162 行：“展品模式只重组既有说明信息，不提供实时数据、仪表盘或虚构读数” | **立场冲突**，要先决定是否放开 |
| 绿／黄／红状态色 + 模拟火警／UPS 切换／未授权进入 | `README` 162 行：“供电与制冷只讲正常工作：不模拟电网故障、UPS 切换、电池充放电时序”；`HANDOFF.md` 硬约束 1：“不引入虚构数值、仪表盘或实时数据” | **立场冲突**，同上 |
| 图层开关／按系统筛选／单类显隐 | `App.jsx:20` 的 `LAYERS` 已被刻意常量化；`README` 27 行：“页面没有…图层开关” | 设计回退，需明确是否推翻 |
| 异常告警模拟 | 现有文案与 note 全部按“正常工作”撰写，加告警会出现“面板说正常、场景在报警”的自相矛盾 | 需连带改写文案与 note |

判断：这不是“加个开关”能解决的。要么承认本工程从“工作原理讲解”升级为“运维演示”，一并改掉 6 个系统的 `description` 与 4 条 `note`；要么把状态层做成**纯结构表达**——设备角色、连接关系、容量位置，不出现温度数字、负载百分比、告警计数。**建议后者**，理由：数字孪生最容易被质疑的就是“这些数字哪来的”，而本项目没有任何真实数据接口，一旦出现 `24.6 °C` 就必须标注“模拟”，标注之后它就不再是孪生，只是动画。

## 五、建议的改造批次

排序依据：可见增量 ÷ 改动面。每加一类设备，成本是 `Blender 脚本 + GLB 节点 + data 条目 + 机位 + 面板 + 回归项`，所以先做“小而独立”的，后做“改链路”的。

**批次 A — 消防与安防（视觉增量最大，不碰既有链路）**
- 烟感／温感探测器：`primitives.jsx` 拼装，直径 ≤ 0.08，挂 `y ≈ 2.9`，沿两排机柜各 3 只
- 声光报警器 × 2（左后墙、右前入口）
- 气体灭火钢瓶柜 × 1：右侧空地（`FloorProps` 已占右前，需挪位置），独立机柜造型，走 Blender 或纯几何
- 消防管路：细管沿 `y = 2.9` 走，避开母线 `2.86`
- 摄像头 × 2 + 门禁读头 × 1 + 电锁：纯几何，入口处新增一个“门框模块”（不封闭场景）
- 数据：`src/data/safetySystems.js`，7 个节点，每个带 `role/input/output/partners`
- 面板：复用 `SystemPanel`，新增 `systems.js` 一条 `id: 'safety'`
- 回归：新增 `verify-safety.browser.cjs`，约 20 项

**批次 B — 网络安全设备（改 N01 内部，不改房间布局）**
- `network-rack.glb` 内部增加防火墙／边界路由／管理交换机三块面板，或纯几何贴在机柜前面板
- 三条网络分离：业务（蓝）／管理（灰绿）／存储（紫），`FlowLegend` 加两类
- 存储交换机：补计算↔存储之间的交换层，修正现在“看起来直连”的问题

**批次 C — 备用电力（改供电链路，风险最高）**
- 柴油发电机 + ATS + 日油箱，放在建筑外侧新增的小平台（`FloorProps` 旁）
- 第二条进线 + UPS 双输入，改写 `supportSystems.js` 的 `FEED` 与 `powerSteps` 第 1 步
- 此时才需要 `README` 与 4 条 `note` 的连带改写

**批次 D — 备份与容灾**
- 备份服务器 + 独立备份存储，挂在 S02 旁；`requestFlow` 不动，另开一条可选路径

## 六、验收与回归影响

- 基线：8 组 346 项（support 83 / request 104 / immersive 44 / server 16 / responsive 25 / fallback 10 / resources 4 / present 60）。
- 批次 A 不改动任何既有节点与路径，理论上 346 项应全绿；若 `overview` 取景因新增机柜需要放宽，`verify-immersive` 的同机位对照图会变，需重出 `outputs/compare-chapters.png`。

- 新增几何一律复用 `floorFade.js` 的世界坐标衰减，不引入不透明硬边。
