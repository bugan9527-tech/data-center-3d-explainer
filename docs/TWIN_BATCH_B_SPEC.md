# 批次 B 实施记录：网络柜补全与三张网

状态：**已完成**。目标是把 N01 从“接入层一台交换单元”补成有边界、有安全、有存储与管理平面的机柜。

## 一、为什么不重排布局

最初的设想是重做机柜前视图，把四台新设备按 U 位整齐排下来。做完几何推导后放弃了，原因很具体：**11 步请求流程的设备锚点是写死的世界坐标**。

`requestFlow.js` 里 `ingress`／`fabric`／`egress`／`storagePort` 四个节点的锚点分别是 `y 1.29 / 1.48 / 1.29 / 1.29`，全部落在主交换单元目前的位置（`z 1.29`）。主交换单元只要下移 0.2，这四个锚点、所有经过它们的路径点、`nodeDescriptions` 的指向、以及 `verify-request` 的 104 项断言都要跟着改。

所以改成**填空档**：不移动任何既有部件，把四台新设备塞进原布局本来就空着的地方。四段空隙是现成的：

| 空隙 | 范围 | 塞进去的设备 | 实际占用 |
| --- | --- | --- | --- |
| 配线场上方 | `2.0 – 2.1575`（顶盖与横梁） | 边界路由器 | `2.015 – 2.145` |
| 配线场与主交换之间 | `1.405 – 1.56` | 防火墙 | `1.415 – 1.545` |
| 主交换与备用交换之间 | `1.075 – 1.175` | 存储交换单元 | `1.0825 – 1.1675` |
| 理线区与备用交换之间 | `0.725 – 0.845` | 管理交换单元 | `0.735 – 0.835` |

最窄的一段只剩 **5 mm** 余量（存储交换上下各 2.5 mm，即 0.0025 世界单位）。这是刻意的：宁可贴紧，也不动既有部件。

## 二、四台设备的建模要点

改的是 `blender/source/generate_equipment.py` 的 `NETWORK_PARTS` 与前视图段：

| 部件 id | 名称 | 特征 |
| --- | --- | --- |
| `part_edge_router` | 边界路由器 | 4 个广域口 + 链路灯，右侧一个控制台口（蓝） |
| `part_firewall` | 防火墙 | 前面板 6 条散热格栅 + 2 个状态灯，左侧旁路口（蓝） |
| `part_storage_switch` | 存储交换单元 | 6 个存储口，用 `teal` 材质与业务口区分 |
| `part_mgmt_switch` | 管理交换单元 | 10 个高密度管理口 |

都沿用既有的 `box()` + `bevel` 与四组材质（`silver`／`black`／`led`／`teal`／`blue`），没有新增材质，所以 GLB 的材质数仍是 10。

## 三、三张网怎么表达

需求书要求“区分业务、管理、存储三张网，不要把线路无差别连在一起，并支持高亮特定网络路径”。本批次按当时的「结构表达」口径只做到前一半（注：该口径已于 2026-11-03 02:55 改为「模拟数据 + 标注」，按网络高亮一条后来由 HUD 的“动态数据流”开关部分覆盖）：

- **设备层**：存储与管理各有独立交换单元，物理上就是两台不同的设备；防火墙与边界路由器单独成件。
- **文案层**：网络系统的 `structure` 改为“业务、存储与管理分走三台交换单元：边界路由器与防火墙把住出口，存储交换只连计算与存储，管理交换只承载带外管理”。
- **不做**：没有按网络切换的高亮，没有图层开关。`LAYERS` 仍是常量，单一视图的设计没有被推翻。

**必须说清的简化**：11 步流程里，读取仍然走 `C 端口组 → 主交换单元 → 存储控制器`，**没有**改走存储交换单元。这两件事在真实机房里是矛盾的（有独立存储交换就不该绕业务交换），所以在部件职责里如实写明“本例为便于讲解，读取流程仍从 C 端口组经主交换单元转发”，而不是留一句看起来正确、实际与场景不符的话。防火墙同理：请求路径画的是直接经 A 端口组，不展开逐条规则。
