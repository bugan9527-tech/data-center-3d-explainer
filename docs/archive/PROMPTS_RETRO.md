# 项目提示词总结

这份文档回答两件事：**这个项目每一轮是怎么被"说"出来的**，以及**哪些说法真的管用**。

项目本身没有 AI 运行时——提示词全部用于驱动编码智能体改这个仓库。五个阶段一共留下三份提示词存档（视觉升级、流动优化、逐件拆解）、一份交接提示词，以及两批数字孪生改造的任务书。原文都在 `docs/archive/`，本文做归纳与复盘。

---

## 一、提示词的四层结构

所有阶段都沿用同一套分层，只是内容随项目长大而变重。

| 层级 | 作用 | 出现位置 | 典型长度 |
| --- | --- | --- | --- |
| 开场提示词 | 让新会话建立正确的项目认知，禁止直接动手 | 每轮第一句 | 20–30 行 |
| 步骤提示词 | 只做一步，做完停下等确认 | 每轮一个 | 20–40 行 |
| 反馈提示词 | 不通过时精准返工，禁止顺手改别的 | 出现问题后 | 3–5 行 |
| 交接提示词 | 换人或换窗口时把状态交出去 | 阶段之间 | 15–25 行 |

开场提示词的标准骨架（三份存档几乎一致）：

1. **坐标**：`工作目录 D:\CodexProjects\PCAssemblyLab：Vite + React 19 + three.js 的数据中心三维教学展品。`
2. **只读清单**：按顺序列出 6–10 个必读文件，先文档后源码。
3. **复述校验**：`读完用不超过 15 行复述：…（关键事实清单）…与仓库实际代码不一致时先指出来，不要照抄文档。`
4. **单步停机**：`然后只执行 … 的 S0，做完立刻停下等我确认，不要继续 S1。`
5. **硬约束**：5–6 条不变式（见第二节）。
6. **环境与命令**：dev／preview 端口、回归命令、Blender 路径。
7. **交付清单**：改了哪些文件、build 结果、回归项数、同机位截图路径。

第 3 条是整个体系里性价比最高的一句。它把"文档漂移"挡在施工之前：接手方必须先证明自己读懂了现状，对不上就先质疑文档。项目后期文档与实现多次脱节（四模式、346 项、12 个节点、旧机位），都是靠这句在开工前拦下来的。

## 二、贯穿全项目的硬约束

这些约束从第一阶段写到最后一阶段，措辞微调但语义没变，是提示词里最该原样保留的部分。

1. **教学结构不变**：11 阶段请求流程、供电 6 步／制冷 7 步的步骤划分与文案口径不得改动。
2. **动画必须可冻结**：`暂停时两次画布截图必须完全一致；减少动态效果下不得有连续动画；演示结束不自动循环。`
3. **响应式与可达性**：`窄屏（375/768）无横向溢出；键盘可完成主要操作。`
4. **不擅自扩依赖**：`除方案明确允许，不新增运行时依赖、不引入外部贴图或模型。`
5. **镜头纪律**：`镜头只能由明确按钮触发，普通选择不移动镜头；进入服务器内部后返回要保留视角与状态。`
6. **测试不能迁就实现**：`改断言必须说明是行为变更，不允许为过测试迁就实现。`（逐件拆解阶段写成"六组原有回归语义不能被'改测试迁就实现'破坏"）
7. **不造不可达的东西**：`不创建界面无法到达的机位、道具或数据。`

第 6 条尤其关键。回归项在项目里被反复重编（280→286→333→346→357→179+34），如果每次都允许"改断言让它过"，脚本早就失去意义。提示词里明确禁止，并要求改动必须伴随行为变更说明。

## 四、逐阶段要点

### 阶段一：功能骨架（未存档）

这一阶段的提示词没有落盘，但从 `PROJECT_PLAN.md` 与验证文档能还原它的结构：**要什么 + 不要什么 + 怎么证明**。

- 要："用可旋转的三维机房，解释工程里各个部分的职责、输入输出与协作过程。"
- 不要："只讲正常工作原理，不模拟电网故障、UPS 切换、电池充放电时序、CFD、温度场。"
- 证明："所有截图来自真实运行页面"；"窄屏 375 无横向溢出"；"减少动态效果时停止移动标记"。

写"不要什么"比写"要什么"更能约束实现。这一阶段每一份验证文档的"本轮目标与边界"小节，本质都是提示词里"不要"那部分的回执。

### 阶段二：视觉与镜头（S0–S10，`archive/UPGRADE_PROMPTS.md`）

**形态**：先建基线（S0），再逐步改，每步一个提示词。每步都是同一个模板：

```
只改 <文件>，不改 <不该动的>。
1) 具体参数：<旧值> → <新值>
2) 具体参数 …
约束：<不变式>
验收：build 通过；回归全绿；截图 outputs/after-xxx.png 与 before 同机位对比。
```

**写得最值钱的一句**在 S4：

> 先看清取景规则：`RoomCameraRig` 的 fit = `min(视口宽/pose.width, 视口高/pose.height)`。桌面端和横屏端实际是被 height 卡住的，只收 width 不会改变构图。

它把"改个数字"变成"先理解约束再改数字"。同类写法还有 S3 的"基座不要外扩——外扩会越过淡出带，必然把硬边带回来"，以及 S6 的"某步骤改指向新机位后，原专用特写若已无任何步骤或脚本引用（先 grep 确认），直接删除，不留不可达的机位数据"。

**落地结果**：光照重配（ambient .55／hemi .5／主光 2.7／ACES 曝光 1.02）、CSS 渐变 + 雾 + 64×64 径向淡出贴图、基座与道具内收、总览 width 15.2／height 10.8／target x +0.4、墙面按世界 Y 淡出、正交改透视（总览 fov 14）、11 个机位覆盖 13 个功能节点、弧线运镜（章节 1.2s／特写 0.9s／复位 0.5s，抬升 8%）、三流头流光、展品模式。

**留下的教训**：提示词里写死的数值必须允许被测量推翻。S10 复盘时发现"12 个功能节点"的口径是错的（实际 11 个机位覆盖 13 个节点，排风与回风共用热通道机位），从此文档改成"按实际数据核准"。

### 阶段三：流动表现（P0–P2，`archive/FLOW_PROMPTS.md`）

**这一阶段的提示词是先测量、后写词**。原文把实测表格直接写进了任务：

| 场景 | 连续 4 帧画布去重 | 结论 |
| --- | --- | --- |
| 供电播放中 | 4 / 4 各不相同 | 画布每帧都在重绘 |
| 供电暂停 | 1 / 4 | 暂停确实冻结 |

结论："不是没动画，而是动画的视觉量级不够、位置不合适。"随后才是 4 条根因（只有一个流头、只有最长路径有流头、贴图太软太大、静态箭头不参与播放）。

**改法提示词**写到了实现级：三个相位错开的流头 `(progress + i/3) mod 1`、核心实心 0.16–0.2 世界单位、次要路径 0.6 倍大小与 60% 不透明度、箭头沿线巡游、6–8 段流动虚线、`reducedMotion` 时固定在 1/4、1/2、3/4。

**验收口径**同样可执行：`供电第 1 步与第 4 步各连拍 6 帧，6 张互不相同；暂停后连拍 6 帧完全一致。`

**落地结果**：P0（三流头 + 巡游箭头 + 虚线）、P1（主干抬到 y=.16、送风口向上短弧、冷暖半透明带、7 个青→暖插值点、风扇旋涡短线）、P2-3（支撑基底机位）、P2-1（播放收成 64px 迷你条）、P2-2（播放开始／切步自动切本步特写）。

**这里出现了一次提示词与用户意愿的偏离**：附录 D 原本写着"P2-1 与 P2-2 会改变现有交互约定，未经我同意不要做"，但 P2-2 后来由用户口头追加并实施。教训是**约束句要跟着决策走**，决策变了要回写文档，否则下一个人会照着旧约束把功能当成违规。

### 阶段四：逐件拆解（S1–S4，`archive/TEARDOWN_PROMPTS.md`）

**提示词从"查现状"起步**，而不是从"改什么"起步：

> 现状：`server_bank` 下面按**材质**合并成 7 块网格，前端拿不到单台。而脚本里每台服务器是逐件创建的。结论：不需要重做模型，只需要改 join 策略。

这个判断直接决定了后面所有步骤的形态。模型侧提示词给出硬契约：`part_server_01…09`（从下到上、两位补零）、`part_fan_tray`／`part_pdu` 两个零三角形锚点、原点必须移到几何中心（否则前端沿 +z 拉出会歪）、三角形数不得增加。

前端侧提示词把三个坑写在了前面：`scene.clone(true)` 共享材质（直接改 opacity 会让九台机柜一起变透明）、只拆主柜（否则同类第二台外壳滑出与邻柜重叠）、`node.position` 自带非零基准（必须先存 `base` 再叠偏移）。

**验收**：GLB 顶层契约不变、三角形数与改造前相同、同机位外观逐像素一致（允许 ≤0.5% 差异）。

**落地结果**：11 件拆解、编号点、单标签 + 引线、规格卡、聚焦机位、已拆解 n/n、全部合上。S2 首轮出现三处标签出界（PDU 标签 y=1053 > 900、风扇标签压左栏、低处部件圆点落到地板），返工方式是把实测值写回提示词：标签钳在画布内、低处偏移降到 0.12–0.15、风扇聚焦点光降到 1.6。

### 阶段五：数字孪生（批次 A–D + 需求书对账）

**这一阶段最有价值的不是施工提示词，而是"先对账"这个动作**。`TWIN_UPGRADE_REVIEW.md` 把外部需求书逐条判成四类：已有、重复建设、真正缺口、立场冲突。结论很直白：

> 需求书是一份合格的"机房应该有哪些系统"的清单，但它是一份**只看过截图、没看过代码**的清单。

冲突被分成两种性质：**立场冲突**（要不要出现读数、告警）与**设计回退**（要不要恢复图层开关）。前者必须先决策，后者可以先做。这条分类法后来直接决定了"模拟数据 + 逐处标注"的折中方案。

**批次排序原则**：可见增量 ÷ 改动面，所以先做"小而独立"，后做"改链路"的。

| 批次 | 内容 | 提示词里的关键论证 |
| --- | --- | --- |
| A | 消防与安防 | 纯 primitives 拼装，不占 GLB，不碰任何既有链路 |
| B | 网络柜四件 | 不移动任何既有部件，把设备塞进原布局的空档——因为 11 步锚点是写死的世界坐标，主交换单元下移 0.2 就要改 104 项断言 |
| C | 发电机 + ATS + 双路市电 | "室外"只能是地板之外；三个候选位置都因遮挡或占位被否，最终选右侧 |
| D | 备份与容灾 | 备份设备必须独立成柜，塞进 S01 就是"本地备份混主存储"的错误示范 |

**一次真实事故**：批次 C 施工期间，另一个窗口把界面重构成了数字孪生看板（含 CPU、温度、功率读数），与本轮早先"结构表达、不做数字"的口径正相反，导致 README 与实现自相矛盾。处理方式：`已于 2026-11-03 02:55 拍板：以看板为准`，同时改写 README 的范围限制与评审文档，并给批次 A 任务书加变更说明。**由此产生第一条跨窗口规则：口径变更必须同轮回写 README，否则文档立刻变成错误文档。**

**落地结果**：八个系统、九台机柜（含 B01）、室外电力平台、双路市电、消防安防七类设备、深色 HUD 三栏、模拟读数逐处标注、八套回归 179 项 + `verify-twin` 34 项。

### 阶段六：交接（`archive/HANDOFF.md`）

交接提示词 = 开场提示词 + 进度快照表 + 硬约束 + 常用命令。它的价值在于"可核对"：接手方先复述，与快照不一致就先指出来再动手。

代价是快照会腐烂。这份交接写的是"4 个展示模式、346 项"，而当前是"无模式标签、179+34 项"。所以现在的规则是：**交接只给判断依据和约束，计数一律写"以脚本输出为准"。**

## 六、复盘：哪些写法有效，哪些失效

| 写法 | 判断 | 证据 |
| --- | --- | --- |
| 先只读 + 15 行复述，对不上先质疑 | **有效** | 多次拦下文档漂移（四模式、346 项、12 节点） |
| 只做一步，做完停下 | **有效** | 一次贴多步时，截图与回归会被跳过 |
| 给实测根因，再给改法 | **有效** | 流动优化先证明"画布在动"才没走错方向 |
| 把"不要什么"写清楚 | **有效** | 边界清单一出现在验证文档里，范围就没失控过 |
| 诊断契约（`data-camera`／`data-flow`／`data-support`） | **有效** | 界面大改后回归仍能定位问题 |
| "以测量为准，不照抄旧参数" | **有效** | 发现 fit 被 height 卡住、节点计数 12→13 |
| 禁止"改测试迁就实现" | **有效** | 回归重编五次，语义没被稀释 |
| 在提示词里写死检查项总数 | **失效** | 280／286／333／346／357／179+34 六种口径，全部很快过期 |
| 一次贴多个步骤 | **失效** | 施工方容易跳过对照截图与全量回归 |
| 多窗口并行、口径未先统一 | **失效** | 批次 C 的看板 vs 结构表达冲突，事后返工并改写文档 |
| 交接快照写死界面形态 | **失效** | "四模式／纯净视野"在交接后两轮内就废弃了 |
| 用绝对路径引用参考素材（桌面视频） | **有条件有效** | 素材只作视觉依据，不能当功能证据，提示词必须写明 |

### 三次口径变更

| 时间 | 变更 | 影响 |
| --- | --- | --- |
| 11-01 | 正交相机 → 透视相机 | 机位需要 fov，`zoomRatio` 改为归一化系数 |
| 11-02 | 四展示模式 → 无模式标签，由 HUD 承担筛选 | 旧回归脚本整体归档 |
| 11-03 02:55 | "不出现任何读数" → "允许读数但逐处标注模拟" | 三份提示词存档同步加历史横幅，README 范围限制重写 |

每次变更都做了同一件事：**改实现 + 改 README + 给旧文档加横幅**。这三件缺一件，文档就会变成"错误文档"。

## 七、如果要开新一轮

1. 读 `README.md` 与 `docs/README.md`，确认现状与归档边界。
2. 用第五节的"开场"起手，把 `<下一步>` 换成具体一步。
3. 一次只发一步；每步验收看四件事：build、回归项数、同机位截图、控制台 0 error。
4. 通过就发下一步，不通过用"返工句"，把现象写成带数值的一句话。
5. 收尾时回写 README，必要时把过程文档移入 `docs/archive/` 并加横幅。
